Can SQL alone catch Medicare providers billing from two countries at once?

A provider cannot be in two countries at once. So I joined the claims table to itself, looked for a US claim and a foreign claim for the same provider with overlapping dates, and scored what turned up. Then I re-ran it and found three things that did not add up. All data here is synthetic.

In plain English I used SQL to find medical providers billing from two countries at once, then found the date maths was broken and the database was out of date.

How the score works

Each flagged provider gets points for each overlapping US and foreign claim pair, for overlap days, for charges above five times the Medicare allowed amount, for large payments, and for appearing in three or more countries. The query is queries/03_risk_scoring.sql in the repo, unchanged.

score = 3 per pair + min(overlap days, 15) per pair
      + 2 if max charge ratio > 5
      + 2 if payments > $10,000
      + 3 if 3 or more countries

    What re-running it found

    1. The overlap days are always zero. The query subtracts two ISO date strings, and SQLite turns each into a number by reading only the leading year, so the result is 0 for every pair in the shipped database. The "plus one per overlap day" part of the score never fires. Switch the demo to "Dates fixed" to see the scores with julianday() doing the subtraction: 18 of the 18 providers change score and 15 reach HIGH. With real overlap days nearly everyone clears the HIGH line of 12, so the 12 and 6 cutoffs would need recalibrating too.
    2. The README does not match the database. It says 7 providers score HIGH. The shipped claims.db gives 1, and with dates fixed 15.
    3. The database is older than the data generator. The generator was fixed in September to create genuinely overlapping windows and the CSV was regenerated (9,936 claims). The database was not, so the dashboard and the README describe the older data. Loading the CSV the way the README says gives 200 flagged providers, not 18.
    Why this matters: a score that silently ignores one of its inputs still produces a tidy ranked list. Re-running a pipeline against its own claims is how these show up.

    What I changed, and what the fixed version shows

    I fixed the date arithmetic, rebuilt the database from the CSV, and added a rule-free check next to the overlap rule: a z-score of each provider's average charge ratio against peers in the same specialty. The generator also records which providers it planted, so both can be scored. On the rebuilt data (9,936 claims, 2,000 providers, 200 planted):

    Read this carefully: the overlap rule scores perfectly because the generator plants exactly that pattern. It tests the plumbing, not real-world accuracy. The peer screen never looks at country or dates, so catching 83% of the planted providers is the more honest signal. Real work would need real labels, such as the OIG exclusion list.

    Published work on Part B data takes the same route: outlier screening first, then models trained on exclusion list labels, with heavy class imbalance. CMS's own Fraud Prevention System savings were disputed, with CMS reporting 5 to 1 and OIG's adjusted figure $1.34 per dollar, so outcomes need tracking whatever the model.

    How I would catch more

    • Foreign-to-foreign pairs and a travel-time check, not just US against foreign.
    • Impossible workload: more than 24 hours of time-based services billed for one provider in one day.
    • Upcoding against peers: each provider's share of top-level visit codes against their specialty norm.
    • Links between providers: shared addresses, bank accounts or referring NPIs, as a graph.
    • External lists: the OIG exclusion list, and claims for deceased patients.
    • A model on top of these features, judged by precision among the top 20 referrals, not accuracy.
