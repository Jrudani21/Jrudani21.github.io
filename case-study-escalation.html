When does a free AI model need a critic? A small, honest benchmark

I route work to free model lanes first and escalate only when needed. I wanted numbers instead of a feeling, so I scored five small coding tasks with hidden tests and no model judges, and compared a free model alone, a free model with a critic, and a strong model alone.

First, what this is not

This is not a leaderboard. There are five tasks and one to five samples per cell, and the same model flipped between pass and fail across samples. It is a worked example of how to measure a routing decision without fooling yourself.

The tasks

Each is a bug class I have actually hit: parsing durations like 1h30m; merging touching intervals; replacing one line without changing its CRLF or LF ending; deciding whether a shell command is a recursive force delete (the check a safety hook needs); and quoting a path for PowerShell, including the typographic quote characters PowerShell treats as quotes.

How it was scored

  1. Hidden test cases run in a subprocess. No model grades another model.
  2. The tests were tested first. A known-good and a known-bad solution had to score full and not-full, so a zero means the model failed, not the harness.
  3. Lane checks. I read the CLI's usage file to confirm which provider really answered. A fallback model's answer was discarded, not counted.
  4. Test-blind critic. The critic sees only the spec and the draft. The loop stops when the critic finds nothing, never because tests passed, and is capped at two rounds.

  • A critique only helped when it named a failing input and the exact required output. Vague review did nothing for the small model.
  • The critique model mattered more than the fixer. A free critic once approved a draft that was still wrong.
  • For a narrow task, routing to a bigger free model beat adding a review step.
  • The critiques also found real defects my first tests never checked, such as a lone carriage return and quoted flags in shell commands.
A caveat I kept in the data. I then wrote stricter tests from rules the spec already stated. They came after I had read the critiques, so I report them beside the first scores and not instead of them.

A side finding that nearly poisoned the numbers

The agent CLI auto-loaded a brainstorming skill, which made a small model answer with a design plan and no code. A scorer that did not read the replies would have counted that as a model failure. Running with the CLI's safe mode removed it: 8 seconds instead of 33, and 21k tokens instead of 51k. I then disabled the two skill plugins in my config and checked one real call.

What I would claim, and what I would not

I would claim: critique quality beats fixer quality; reviews need a failing input and an exact expected output; thin tests hide defects a review finds; and checking which model actually answered is part of the method.

I would not claim anything about cost in dollars (free calls were $0 and I have no price for the strong calls), nor that this generalises past five tasks.
